# QuantTrading 详细重构路线图

> 目标：将当前项目从研究型原型逐步升级为“可信回测 + 安全模拟盘 + 可控小额实盘”的交易系统。
>
> 原则：先保证数据、订单、仓位和风控的正确性；再扩展策略、模型和可视化。任何不能通过回放和 sandbox 验证的功能，不进入真实资金环境。

---

## 1. 目标能力与非目标

### 1.1 第一阶段目标能力（MVP）

- 对固定历史数据可重复地产生同样的回测结果。
- 回测和行情回放模式产生同样的状态、信号和订单意图。
- 实盘只使用已收盘 K 线，每根 K 线最多处理一次。
- 订单、仓位、已处理 bar 与熔断状态可在重启后恢复。
- 支持一个交易所、现货或合约中的一种模式、少量标的的 sandbox 运行。
- 能查看运行状态、订单、成交、仓位、权益、风险和异常。

### 1.2 本阶段不做的内容

- 机器学习预测或自动训练；当前 `models/` 仅为占位，不能作为基础能力依赖。
- 多交易所套利、高频交易、跨币种保证金、复杂期权策略。
- 大额真实资金或无人值守生产部署。
- 以提高历史收益为目的的策略参数优化。

## 2. 交付阶段概览

| 阶段 | 名称 | 预计工作量 | 核心交付 | 放行条件 |
| --- | --- | ---: | --- | --- |
| 0 | 工程基线 | 2-4 天 | 编码/依赖/测试/基准记录 | 可重复安装与测试 |
| 1 | 数据与时间语义 | 4-6 天 | 统一 K 线、时区、收盘判定 | 无未来数据与重复 bar 测试通过 |
| 2 | 回测可信度 | 1-2 周 | 可审计撮合、费用和多标的时间轴 | 回测回归基线稳定 |
| 3 | 订单与状态恢复 | 1-2 周 | 订单状态机、持久化、恢复 | 重启和超时不重复下单 |
| 4 | 组合风险控制 | 4-7 天 | 全组合估值、熔断、限制 | 风控场景测试通过 |
| 5 | 引擎统一与架构重构 | 1-2 周 | 共享事件流与适配器接口 | 回放与回测一致 |

## 3. Phase 0：工程基线

### 目标

保护既有工作区，明确当前系统的可运行状态，防止后续重构失去比较对象。

### 工作分解

| 编号 | 工作项 | 交付物 | 验收标准 |
| --- | --- | --- | --- |
| P0-01 | 盘点目录、依赖、入口和生成物 | 文件清单与保留策略 | 明确哪些是源码、测试、报告、缓存、历史资料 |
| P0-02 | 统一新增文件格式 | `.editorconfig` | 新增文件默认 UTF-8/LF；不批量覆盖已有未提交文件 |
| P0-03 | 生成物管理 | `.gitignore` 更新方案 | 缓存、临时日志、运行报告默认不进入 Git |
| P0-04 | 测试基线 | 测试运行记录 | 记录通过/失败数量及失败原因 |
| P0-05 | 固定回测样本 | synthetic 基准报告 | 固定参数可人工复核 |
| P0-06 | 依赖复现 | `requirements.lock.txt` 验证记录 | 新环境可安装并执行测试 |

### 当前状态

- 已创建格式规范和测试/回测基线文档。
- 当前测试：41 项中 40 项通过；`test_no_lookahead.test_execution_timing` 未生成预期交易，需在 Phase 1 前修复或重新定义夹具。
- 工作区存在大量既有未提交变更，因此删除历史报告、缓存或 archive 前必须单独确认。

### Phase 0 退出条件

- 可以准确复现当前测试结果。
- 生成物和源码的边界已明确。
- 所有既有改动已由用户确认保留、提交或清理。

## 4. Phase 1：数据与时间语义

### 目标

统一“何时一根 K 线可被使用”的规则，消除实盘信号抖动和未来数据风险。

### 设计决定

1. 每个 `Bar` 必须包含 `symbol`、`timeframe`、`open_time`、`close_time`、OHLCV、来源和完整性标记。
2. 策略只能消费 `is_closed=True` 的 bar。
3. 每个 `(symbol, timeframe, close_time)` 只处理一次。
4. 回测的 bar 结束事件与实盘已收盘 bar 事件必须具有同一语义。
5. 所有内部时间使用 UTC；仅在展示层转换到本地时区。

### 工作分解

| 编号 | 工作项 | 关键实现 | 验收测试 |
| --- | --- | --- | --- |
| P1-01 | 统一时间索引 | `DatetimeIndex` 强制时区与排序 | 混合时区输入被规范化或拒绝 |
| P1-02 | 完整 K 线过滤 | 根据 timeframe 和当前时间过滤 CCXT 最后一根未收盘 K 线 | 形成中的 K 线不触发信号 |
| P1-03 | Bar 去重 | `last_processed_bar` 按标的持久化 | 重复 tick 不重复下单 |
| P1-04 | 数据质量状态 | 缺失、重复、延迟、异常 OHLCV 标记 | 质量异常可阻止新开仓 |
| P1-05 | 回放数据源 | 历史 bar 按时间逐条推送 | 回放结果与回测信号一致 |
| P1-06 | 修复无未来函数测试 | 最小可控测试夹具 | 明确验证信号时间与成交时间 |

### 退出条件

- 未收盘 bar、重复 bar、乱序 bar、缺失 bar 均有自动化测试。
- 回测和回放在相同数据上得到相同 `Signal` 序列。

## 5. Phase 2：可信回测

### 目标

把“回测收益”变成可解释、可复盘的模拟结果，而不是不透明的净值曲线。

### 工作分解

| 编号 | 工作项 | 关键实现 | 验收标准 |
| --- | --- | --- | --- |
| P2-01 | 多标的交易日历 | 使用统一时间轴；区分可估值与可成交 | 单标的缺 bar 不删除全组合时间点 |
| P2-02 | 订单撮合规则 | 明确 market/limit/stop 在开盘、盘中、跳空时的填充逻辑 | 订单情景测试覆盖跳空和未触发 |
| P2-03 | 成交量与部分成交 | 根据 bar volume 限制成交数量；未成交订单继续或撤销 | 交易数量不会超过可成交流动性 |
| P2-04 | 成本模型 | 手续费、滑点、冲击成本、funding/借币成本可配置 | 每笔交易可分解全部成本 |
| P2-05 | 熔断执行语义 | 触发后撤单、禁止开仓、只产生一次平仓意图 | 熔断场景不会重复提交订单 |
| P2-06 | 回测审计日志 | signal/order/fill/equity 四类记录 | 任意成交可从报告追溯到信号 |
| P2-07 | 报告质量 | 策略、状态、标的、费用和暴露归因 | 报告可解释结果来源 |

### 回测必备指标

- 总收益、CAGR、波动率、夏普、Sortino、最大回撤、Calmar。
- 交易次数、胜率、盈亏比、期望、平均持仓时间、换手率。
- 毛收益、手续费、滑点、冲击成本、funding/借贷成本。
- 最大杠杆、平均现金占比、最大单标的暴露、状态/策略贡献。

### 退出条件

- 回测输出具有版本、配置哈希、数据范围和随机种子。
- 每次代码修改能对固定数据集执行回归比较。
- 关键策略在样本外数据中完成最少一次验证。

## 6. Phase 3：订单生命周期与状态恢复

### 目标

让系统在网络抖动、部分成交、重启或交易所延迟下仍保持仓位与订单的一致性。

### 核心领域对象

```text
Signal -> OrderIntent -> Order -> Fill -> Position -> PortfolioSnapshot
```

| 对象 | 最小字段 |
| --- | --- |
| `Signal` | id、策略、标的、bar 时间、方向、原因、建议止损/目标价 |
| `OrderIntent` | signal id、数量、订单类型、价格、风险检查结果 |
| `Order` | client order id、交易所订单 id、状态、请求时间、更新时间 |
| `Fill` | order id、成交数量、成交均价、手续费、成交时间 |
| `Position` | 标的、数量、均价、未实现盈亏、更新时间 |
| `PortfolioSnapshot` | 现金、权益、风险状态、价格时间、快照时间 |

### 工作分解

| 编号 | 工作项 | 关键实现 | 验收测试 |
| --- | --- | --- |
| P3-01 | 订单状态机 | `created/submitted/open/partial/filled/canceled/rejected/unknown` | 非法状态转换被拒绝 |
| P3-02 | 客户端订单 ID | 信号与 bar 时间生成稳定、可查询 ID | 重试不会生成重复订单 |
| P3-03 | 持久化仓储 | SQLite 起步，接口可替换 | 重启后状态完整恢复 |
| P3-04 | 对账流程 | 拉取交易所订单、成交、余额、仓位 | 本地与交易所差异可报告 |
| P3-05 | 超时恢复 | 先按 client order id 查询，再决定重试 | 超时测试不重复开仓 |
| P3-06 | 部分成交处理 | 更新剩余数量和仓位平均价 | 部分成交后风险暴露正确 |
| P3-07 | 应急停止 | 新开仓开关、撤单、可选平仓 | 急停动作可审计 |

### 退出条件

- 强制重启后，系统不会重新执行旧信号。
- 交易所 API 超时和部分成交均能恢复到确定状态。
- 订单链路可以完整审计。

## 7. Phase 4：组合级风险控制

### 目标

在下单前阻止不满足资金、风险和市场规则的交易；风险判断必须基于完整组合。

### 风控层级

```text
数据健康 -> 交易开关 -> 单笔风险 -> 标的限制 -> 资产组限制
           -> 组合杠杆 -> 日内损失 -> 熔断/急停
```

### 工作分解

| 编号 | 工作项 | 规则示例 | 验收标准 |
| --- | --- | --- | --- |
| P4-01 | 全组合估值 | 所有持仓使用同一时点价格表 | 多标的权益计算正确 |
| P4-02 | 仓位规模 | 基于止损距离、风险预算和交易所精度取最小值 | 订单不超过风险/资金限制 |
| P4-03 | 杠杆/集中度 | 总 gross exposure、净敞口、单标的和同方向组限制 | 超限订单在提交前拒绝 |
| P4-04 | 日内回撤熔断 | 保存日初权益；触发后冻结开仓 | 重启后熔断状态仍有效 |
| P4-05 | 市场流动性限制 | 最大订单占 bar 成交量比例 | 低流动性下不产生不可成交订单 |
| P4-06 | 交易所规则 | 最小金额、数量步长、价格精度、市场类型 | 不合规订单本地拒绝 |
| P4-07 | 相关性约束 | 初期按 BTC/ETH 等资产组上限；后期引入滚动相关性 | 同风险方向不会过度集中 |

### 退出条件

- 每一个风控拒绝都有机器可读的原因码。
- 风控参数从配置读取，并被写入每次回测和实盘快照。
- 关键限制在回测、回放和 sandbox 中行为一致。

## 8. Phase 5：统一事件引擎与架构重构

### 目标

减少 `BacktestEngine` 与 `LiveTradingEngine` 的逻辑分叉，把业务流程变为可回放事件流。

### 目标架构

```text
DataAdapter
  -> BarClosedEvent
  -> StateService
  -> StrategyService
  -> RiskService
  -> ExecutionService
  -> Order/Fill Events
  -> PortfolioService
  -> Storage + Reporting + Monitoring
```

### 模块边界

| 模块 | 职责 | 不应承担的职责 |
| --- | --- | --- |
| DataAdapter | 获取、校验、发布已收盘行情 | 策略判断、下单 |
| StateService | 计算 regime | 直接修改仓位 |
| StrategyService | 从已知数据产生信号 | 访问交易所、计算最终仓位 |
| RiskService | 把信号转换为允许/拒绝的订单意图 | 直接网络下单 |
| ExecutionService | 下单、查询、撤单、接收成交 | 决定策略方向 |
| PortfolioService | 根据成交更新组合和估值 | 产生交易信号 |
| Storage | 保存状态和审计事件 | 业务规则判断 |

### 工作分解

- 为各模块定义 `Protocol`/抽象接口。
- 先保留原有策略实现，通过适配层接入新 `Signal` 接口。
- 先使用内存仓储和模拟执行器，再接入 SQLite 与 CCXT 适配器。
- 构建历史回放执行器，作为回测与实盘一致性的测试工具。
- 逐步迁移，不进行一次性重写：每迁移一个模块都保留回归测试。

### 退出条件

- 回测、历史回放和 sandbox 使用相同的策略、风险和订单意图流程。
- 切换数据源或执行器不需要修改策略代码。

## 9. Phase 6：Sandbox、监控与运维

### 目标

在不承担真实资金风险的前提下，证明系统能够长期稳定运行并可被人类监督。

### 最小监控面板

| 区域 | 必须展示的信息 |
| --- | --- |
| 系统健康 | 进程状态、版本、最后心跳、数据延迟、最近错误 |
| 市场数据 | 每标的最新已收盘 bar 时间、价格、状态、数据质量 |
| 策略 | 当前策略、最近信号、信号原因、冷却状态 |
| 执行 | 挂单、最近订单、部分成交、拒单原因 |
| 组合 | 现金、权益、仓位、未实现盈亏、杠杆、集中度 |
| 风控 | 当日起始权益、回撤、熔断状态、急停状态 |

### 工作分解

- 将 `reports/live_status.json` 扩展为版本化、完整的状态快照。
- 增加结构化日志：signal、order、fill、risk、reconciliation、error。
- 增加告警：数据过期、连续 API 错误、订单拒绝、账户不一致、熔断触发。
- 实现日终对账与报告。
- 在 testnet 连续运行 14 天，记录每个异常及恢复过程。

### 退出条件

- 14 天运行中无重复订单、无未知仓位、无未解释账户差异。
- 所有错误可从日志和面板定位。
- 关键告警能在合理时间内通知操作者。

## 10. Phase 7：小额实盘门槛

仅在以下全部满足后才允许小额实盘：

- Phase 1 至 Phase 6 的退出条件全部通过。
- testnet 至少连续运行 14 天，且重启、断网、API 超时、部分成交和熔断均已演练。
- 交易对、交易所、市场类型和风险预算均有明确白名单。
- 初始资金上限、单日损失上限、单笔风险上限和紧急停止负责人均已确定。
- 账户对账差异为零或已有明确解释。
- 有回滚版本和运行手册。

### 上线节奏

1. 单交易所、单标的、现货或 sandbox 已验证的同一种市场类型。
2. 低频策略、低风险预算、单笔小额。
3. 每日人工审核订单、成交、仓位和风险报告。
4. 连续稳定后才增加标的或风险预算；每次只改变一个变量。

## 11. 测试矩阵

| 类别 | 必测场景 |
| --- | --- |
| 数据 | 时区、乱序、重复、缺失、未收盘 K 线、异常价格、数据延迟 |
| 策略 | 指标预热、状态切换、冷却、同 bar 不重复信号、无未来数据 |

| 集成 | 多标的估值、账户同步、对账、回放与回测一致性 |
| 运维 | API 限流、断网、日志失败、磁盘空间、配置错误、密钥缺失 |

## 12. 推荐的前四个迭代

### Iteration A：数据安全（3-5 天）

- 完成 P1-01 至 P1-03。
- 修复 `test_no_lookahead`。
- 新增“未收盘 K 线”和“重复 tick”测试。

### Iteration B：组合与熔断（3-5 天）

- 完成 P4-01、P4-03、P4-04。
- 实盘传递完整价格表。
- 将日初权益和熔断状态写入本地存储。

### Iteration C：订单确定性（5-8 天）

- 完成 P3-01 至 P3-05。
- 引入 SQLite 状态库和 client order id。
- 编写重启、超时和部分成交测试。

### Iteration D：回放与 sandbox（5-8 天）

- 完成 P1-05、P5 的最小事件流和 P6 的状态面板。
- 运行历史回放，对比回测输出。
- 启动 testnet 的持续运行。

## 13. 决策门

| 决策点 | 必须回答的问题 |
| --- | --- |
| 进入 Phase 2 前 | 无未来数据测试是否全部通过？K 线收盘语义是否明确？ |
| 进入 Phase 3 前 | 回测交易是否可完整追溯？是否有固定回归基线？ |
| 进入 Sandbox 前 | 每根 bar 是否只处理一次？风控是否按全组合计算？ |
| 进入小额实盘前 | 订单和仓位能否在崩溃后恢复？是否完成 testnet 长跑？ |
| 扩大资金前 | 对账、告警、回撤和异常处理是否持续达标？ |

## 14. 风险提示

本路线图提升的是系统工程可靠性，不保证策略盈利。任何真实资金使用仍应独立进行策略有效性、交易所风险、流动性、操作安全和合规评估。
