# QuantTrading 重构路线图

## 目标与边界

本路线图的目标是将当前项目从“研究/原型型量化交易框架”逐步提升为：

1. 可重复、可信的回测系统；
2. 回测与实盘信号行为一致的交易系统；
3. 具备基础故障恢复与风控保障的模拟盘/小规模实盘系统。

在完成订单持久化、异常恢复、交易所规则适配和监控告警前，系统不应使用真实大额资金。

## 总体顺序

```text
清理基线
  -> 回测可信度
  -> 实盘安全与一致性
  -> 架构模块化
  -> 研究与可观测性
  -> 生产化能力
```

---

## Phase 0：建立基线（1-3 天）

### 目标

明确保留范围、清理废弃物，并让当前行为可以被重复验证。

### 工作项

- 盘点并确认可删除的 `archive/`、旧验证脚本、历史报告、缓存和重复虚拟环境。
- 统一源码、文档和配置文件的 UTF-8 编码，修复 README 中文乱码。
- 将生成物写入 `.gitignore`：`__pycache__/`、临时报告、日志、本地环境和密钥文件。
- 固化依赖版本，确认 `requirements.lock.txt` 可以重建开发环境。
- 运行全部单元测试，记录当前通过率及已知失败项。
- 为一组固定的 synthetic 数据建立“基准回测结果”，作为后续重构的回归样本。

### 验收标准

- 项目可从干净环境安装并运行测试。
- 固定 seed 的 synthetic 回测能重复得到相同结果。
- 删除项有明确清单，核心代码、测试、配置和一份代表性报告被保留。

---

## Phase 1：可信回测（1-2 周）

### 目标

让回测结果反映明确、一致且可审计的交易假设。

### 工作项

- 明确并测试时间语义：信号在收盘后产生，订单在下一根 bar 执行。
- 改进多标的时间轴：采用统一日历/并集，而不是因单个标的缺 bar 删除全体时间点。
- 区分“可估值”和“可成交”：缺失行情可沿用旧价估值，但不得虚构成交量或成交条件。
- 完善订单撮合模型：部分成交、成交量约束、价格跳空、限价单过期和撤单。
- 将手续费、滑点、冲击成本、funding fee 和借币成本设为可追溯配置。
- 修复并明确熔断行为：触发时撤单、禁止开仓、只提交一次平仓请求，并在报告中披露下一根成交风险。
- 扩展回测报告：交易原因、策略分解、暴露、换手、资金利用率和滑点/费用分解。

### 验收标准

- 回测能通过无未来数据、订单撮合、跳空和多标的缺失数据测试。
- 每一笔交易可追溯至信号、订单、成交和费用。
- README 与实际执行和撮合规则一致。

---

## Phase 2：实盘安全与回测一致性（1-2 周）

### 目标

消除会造成重复下单、错误仓位和失效风控的实盘风险。

### 工作项

- 仅对已收盘 K 线生成信号；不要直接使用 CCXT 返回的最后一根 K 线。
- 实现 `last_processed_bar`，每个标的每根 bar 最多处理一次；将状态持久化以支持重启恢复。
- 每次 tick 建立完整 `current_prices`，按全组合而不是单标的计算权益、杠杆和集中度。
- 将日内起始权益与 circuit breaker 持久化；触发后禁止开仓，并按配置撤单/平仓。
- 将交易所最小数量、最小名义价值、步长、价格精度和现货禁止做空等规则前置校验。
- 区分订单提交、接受、部分成交、完全成交、撤销、拒绝和未知状态。
- 对网络超时采用“先查询后重试”，避免重复下单。
- 先在 sandbox/testnet 连续运行，并保存完整事件日志。

### 验收标准

- 同一根 K 线重复 tick 不会产生新的策略订单。
- 程序重启后不会重复执行旧信号。
- 组合权益、仓位与交易所账户同步一致。
- 断网、API 超时、部分成交和熔断均有自动化测试。

---

## Phase 3：架构重构（1-2 周）

### 目标

降低核心模块之间的耦合，避免回测与实盘逻辑逐渐分叉。

### 目标架构

```text
market_data -> bar_event -> state/regime -> strategy_signal
            -> risk_decision -> order_intent -> execution_adapter
            -> order/fill_event -> portfolio -> reporting/monitoring
```

### 工作项

- 定义统一领域对象：`Bar`、`Signal`、`OrderIntent`、`Order`、`Fill`、`Position`、`PortfolioSnapshot`。
- 定义统一接口：行情源、策略、风控、执行器和状态存储。
- 将 `BacktestEngine` 和 `LiveTradingEngine` 改为共享事件处理流程，仅替换数据源和执行适配器。
- 将配置从全局读取改为显式注入，并增加配置校验。
- 拆分策略信号与下单逻辑：策略只产生信号，仓位计算与下单由统一风控/执行层处理。
- 将路由策略切换写成独立状态机，定义撤单、平仓、冷却和重新入场规则。
- 删除或隔离空壳的 `models/`；只有引入完整训练、验证和推理链路时再恢复。

### 验收标准

- 对同一历史数据，回测和“回放模式实盘引擎”生成相同信号与订单意图。
- 核心模块可替换、可单独单测，不依赖全局文件路径。
- 新增策略不需要修改引擎核心逻辑。

---

## Phase 4：研究、监控与运维（1-2 周）

### 目标

使策略评估、运行状态和异常处理可见、可复盘。

### 工作项

- 建立 walk-forward、样本外验证和参数稳定性分析流程。
- 在报告中加入基准比较、暴露归因、策略归因和市场状态归因。
- 实现 Streamlit dashboard：账户、仓位、订单、最近信号、市场状态、风控、数据延迟和异常。
- 结构化日志与告警：订单拒绝、账户不同步、数据延迟、熔断和连续异常。
- 增加日终对账：本地订单/仓位与交易所数据差异检测。
- 增加安全配置：密钥仅通过环境变量或密钥管理器加载，不允许出现在命令行或报告中。

### 验收标准

- 可在一个界面查看运行健康状态与完整订单链路。
- 策略研究结果能区分样本内、验证和样本外表现。
- 所有关键异常都能留下审计日志并触发告警。

---

## Phase 5：生产化门槛（持续）

### 目标

在小规模真实资金前，建立可控的发布、恢复和风险边界。

### 工作项

- 使用纸面交易和 testnet 完成不少于 2-4 周的连续稳定运行。
- 灰度上线：单交易所、单标的、低风险预算、严格资金上限。
- 增加服务守护、自动重启、状态恢复、备份与版本回滚。
- 实施交易前检查、每日风险报告、异常人工审批和紧急停止开关。
- 定义上线/下线准则：最大回撤、订单错误率、数据延迟、账户差异和策略漂移阈值。

### 验收标准

- 重启、断网和交易所短暂故障不会造成重复订单或未知仓位。
- 风控限制在交易提交前和交易所账户层均可验证。
- 能完整回放任意一天的信号、订单、成交与账户变化。

## 优先级清单

| 优先级 | 项目 | 原因 |
| --- | --- | --- |
| P0 | 已收盘 K 线、bar 幂等、订单状态、完整组合估值、实盘熔断 | 直接影响错误交易与资金风险 |
| P1 | 多标的时间轴、撮合真实性、回测报告、交易所规则 | 直接影响回测可信度 |
| P2 | 事件架构、依赖注入、配置校验、策略/执行解耦 | 降低后续维护成本 |
| P3 | Dashboard、优化研究、机器学习模块 | 提升可用性，不应阻塞安全修复 |

## 建议的第一个迭代

先完成 Phase 0，并从 Phase 2 提取以下五项作为第一个功能迭代：

1. 只处理已收盘 K 线；
2. 每根 bar 只执行一次；
3. 全组合价格与权益计算；
4. 实盘日内熔断与状态持久化；
5. sandbox 下的订单状态测试。

这五项完成后，再开始删除旧模块和进行大规模架构调整，能显著降低重构过程中的交易风险。
