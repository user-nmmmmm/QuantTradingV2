## QuantTrading 架构问题与性能优化 Roadmap

核对日期为 2026-10-02。本文记录本次架构复核、性能测量及改进计划，配合现有统一 Roadmap 使用，不改变策略研究结论或真实资金准入状态。用户要求完成余项后的验收记录见 [后续修复与回测报告](architecture_performance.md)。

本次目标是确认实际交易链路中的逻辑缺陷，建立可复现的回测与行情性能基线，再提高受限速约束的行情并发和调度效率。行情速度同时覆盖数据链路延迟与价格变化速度。

### 3. 并发与限速的具体边界

`run_live.py` 新增 `--market-data-workers`，范围 1 至 8，默认 4。直接使用适配器时默认 1；实盘引擎使用原生 DataFetcher 时默认 4，未知自定义抓取器保持串行，显式配置可覆盖。

并发仅用于各标的的网络读取。抓取结果按输入标的顺序返回，主线程完成原始数据合并、指标更新与状态提交。共享的 pandas 行情视图不由 worker 同时修改；已闭合 K 线交给决策代码前复制，消除了本轮发现的切片写入警告。

每个 worker 独占 CCXT 客户端及 HTTP Session，避免跨线程共享会话。已安装的 CCXT 4.5.35 通过 throttle 钩子传入各 REST 请求的计算权重，本轮公共客户端将该权重交给进程内的交易所节拍器，元数据请求也进入此预算。CCXT 文档说明每个客户端的限速器独立，重复创建实例会重置其状态，故客户端复用和跨 worker 协调需要一起实现。[CCXT 官方 Manual](https://github.com/ccxt/ccxt/wiki/Manual)

此协调覆盖本轮公开 OHLCV 路径，尚未统一私有 Broker、其他历史接口、其他进程和外部程序的 IP 请求预算，相关混合负载验证保留为 AP13。

实盘状态导出新增 `performance`：最近已完成 tick 的耗时、配置轮询间隔、本轮行情总耗时、抓取/计算耗时、失败数、复用/重算数以及逐标的获取耗时。导出发生在当前 tick 内，因此 tick 耗时字段代表此前已完成的轮次。

### 4. 离线行情性能对照

输入为每标的 160 根分钟 K 线；每次抓取明确模拟 20 ms I/O 等待。保留 worker 池，预热在计时外，新旧版本交替运行，每场景 5 对样本；DataFrame 值逐标的核对一致。此基准衡量并发容量和本地计算开销，不代表真实交易所响应或其限速下的可达吞吐。

### 2. 断线、超时与保护的具体语义

首次启动没有游标时只接管最新已闭合 bar，不重新提交历史信号。有游标时，追赶按时间顺序推进，每标的每轮最多恢复配置的历史 bar 数。超过最新快照覆盖范围的断线，原生客户端从游标之前的指标窗口开始取一个有界 REST 页；合并最新快照后分轮推进。真实时间缺口不会被“推进游标”掩盖，只有连续前缀能被恢复。

历史恢复只更新状态识别、路由切换和已观测 bar 的冷却计数；不调用历史撤单、退出或开仓。账户同步与保护单维护继续依据当前交易所事实执行。追赶游标与策略/Router 检查点在同一事务保存，最新 bar 的处理事实也与检查点在同一事务提交。离线用例覆盖滚动窗口、分轮追赶、游标恢复、当前 bar 去重及长断线原生分页回补。

行情预算默认 5 秒，其中 80% 用于并行读取，剩余预算在各标的本地计算前检查。Python 不能强制杀掉已运行的任意自定义读取函数：超时函数可继续占据一个 worker，但没有交易状态写入入口，同标的也不会启动重复残留请求。原生 SDK 的每次 REST 调用使用剩余截止时间约束网络 timeout。操作系统调度、网络实现以及最后一段不可中断的指标计算仍可能超出预算；关闭进程也可能等待非合作的自定义读取。这是可控退出和状态隔离机制，不是绝对硬实时保证。

保护周期默认 5 秒，实际执行在主线程且不可重入。行情读取前及正常/失败退避等待期间都会检查保护任务，防止公共数据长尾独占整个轮询周期。保护任务本身的私有 API 延迟、状态核对耗时及当前不可中断的工作仍可能延后下一次保护，5 秒是调度目标而非保护单保证成交时间。原有账户事实门禁、未知订单恢复和风险准入继续有效。
