# 账户状态迁移与恢复说明

本次实现服务于 P0–P2 修复和离线再验证。策略仍为 `paused_revalidation`；以下操作不构成实盘准入。

## 身份与目录

官方入口要求非秘密账户标识 `--account-id`（或 `QUANT_ACCOUNT_ID`）。交易所、sandbox/live、账户标识、市场类型组成规范身份，其 SHA-256 前 24 位为 `reports/runtime/<identity>/` 目录名。该目录保存订单、风险预算、策略状态、状态导出及告警。不要用 API 密钥作为账户标识。

订单、状态和日风险数据库内部同时绑定完整规范身份。身份不匹配即拒绝打开；非空但没有身份的旧共享数据库不会自动归入某个新账户。旧构造接口保留供离线读取、兼容测试及人工恢复使用，不能将其默认共享路径当成多账户生产配置。

## 增量迁移

订单账本升级为 schema 2。对已有 schema 1 或无版本订单库，升级前通过 SQLite backup API 生成快照并做 integrity_check；新增风险动作 sequence 表，保留已有订单 ID、成交及人工处置记录。订单意图中新字段为可选项，历史记录不猜测初始止损或策略归属。

旧记录缺失初始止损、归属、真实成交明细或手续费换算证据时，成交投影标记恢复问题并禁止新增风险。资产事实与成交投影不一致也进入恢复状态。不要把没有归属的余额手工挂到 TrendBreakout 名下以绕过检查。

恢复旧共享数据库时，应先关闭相关进程、备份全部数据库、核对交易所/环境/账户/市场身份和交易所导出的订单成交。身份无法证明的库保留只读，不合并。当前没有自动批量认领工具；需完成有审计记录的人工事实核验后再构造新账户状态。

## 快照恢复步骤

1. 停止使用目标数据库的所有进程；不要对仍在交易的进程覆盖数据库。
2. 备份目标库及关联订单、风险、策略状态。每个库的快照是独立文件，不能假设不同时间的快照具有跨库原子性。
3. 调用 `validate_database(snapshot, expected_identity=identity)`，检查 SQLite 完整性、账户身份、已知组件版本兼容性。
4. 调用 `restore_snapshot(snapshot, target, expected_identity=identity)`；恢复采用临时库、SQLite backup 和原子替换，拒绝不同账户目标。
5. 在离线环境演练恢复，检查动作 sequence、历史订单 ID、成交去重、lot 数量、现金不重复应用、风险预算和策略状态。
6. 恢复后先执行订单及账户核验；UNKNOWN、缺少成交事实、数量不符、过期实时价格均不允许新增风险。保护恢复与可验证的减仓通路继续工作。

测试 `tests/test_revalidation_recovery.py` 覆盖旧版本备份迁移、身份隔离、损坏/错账户快照及恢复。`tests/test_revalidation_execution.py` 使用离线有状态交易所和真实订单/账户/账本组件验证重放。

## UNKNOWN 与保护恢复

超时、暂时未找到、不支持查询及不完整列表都不能释放风险预留。只有持久化的权威不存在证据，或有身份和理由的人工“从未提交”处置，才能终结相应预留。Binance 精确 client ID 查询的暂时 not-found 仍按不确定处理。

保护单只有交易所明确确认身份、方向、触发价和数量后才能认定有效。非原子替换先等待撤单确认，再提交新的独立 sequence；撤单不确定时保留占用。替换失败触发保护恢复/减仓，不能仅靠日志宣称已有保护。

现货保证金使用可验证持仓及待退出订单限制数量，不能提供合约原生 reduceOnly 的撮合保证。外部手工交易、多进程交易或借贷资格变化仍需账户级独占和交易所事实核验。当前未验证真实 Binance 账户条件单资格、历史保证金额度、逐日利率、跨数据库同步快照或真实网络故障恢复；这些不标记为实盘验收通过。
