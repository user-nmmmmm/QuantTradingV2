# 当前项目架构与问题分析（2026-08-02）

## 架构结论

当前系统是一个以市场状态识别和策略路由为中心、共享策略与风控核心、区分回测撮合和 CCXT 实盘执行的单体 Python 量化交易框架。主链路为：数据获取与校验 → 指标 → 市场状态机 → Router → 策略 → 风控与组合 → 回测 Broker 或 LiveBroker → 报告/状态持久化。

## 当前问题（按优先级）

### P0：真实资金上线阻断项

1. 实盘入口允许通过命令行传递 API Key/Secret（`run_live.py:43-44`），可能泄露到 shell history、进程列表或运维采集；应只允许密钥管理器或环境注入。
2. 实盘错误处理主要是记录异常后继续轮询，尚缺少统一的重试/指数退避、限流、熔断、告警和人工恢复状态机；网络抖动与交易所不确定响应可能造成持仓与本地状态分叉。
3. 订单与账户对账能力仍不完整。存在 `OrderStore`，但当前实盘主链路没有形成“提交前持久化 → 交易所确认 → 重启恢复 → 周期性对账”的完整闭环。
4. `live_status.json` 只适合作为监控快照，不是权威账本；SQLite 也是单机状态，缺少备份、迁移、锁竞争与损坏恢复方案。

### P1：架构一致性与正确性风险

1. 领域模型重复：`core/broker.py` 和 `core/domain.py` 各自定义 `OrderStatus`，容易发生类型与状态迁移语义漂移。
2. 状态存储重复：`core/state_store.py` 与 `core/state_store_v2.py` 几乎同名同责，而实盘引擎直接依赖 v2；缺少清晰迁移边界和唯一公共接口。
3. 回测与实盘虽然共享策略/Router，但使用不同 Broker 接口且没有显式执行端口协议，容易出现“回测可运行、实盘语义不一致”。
4. 研究脚本拥有独立回测逻辑，没有强制复用生产回测引擎，研究结论可能与主系统的费用、时间线和成交语义不一致。
5. 默认配置存在双来源：`config/config.py` 内置默认值与 `params.yaml` 并存；两者费率并不相同，YAML 缺失或加载失败时结果会静默改变。

### P2：工程质量与可维护性

1. `models/features.py`、`labels.py`、`predictor.py`、`trainer.py` 只有空壳类，ML 子系统尚未实现，却作为正式顶层包存在。
2. `dashboard/utils.py` 主要是主题/样式代码，未看到完整 dashboard 应用入口；README 中的监控能力容易被高估。
3. 根目录 `Trading_V1_Model.py`、多个 `verify_*.py` 与 `archive/` 中旧实现并存，增加入口歧义和重复维护成本。
4. 多处捕获宽泛 `Exception`，`main.py` 还有裸 `except: pass`，会吞掉失败原因并降低可观测性。
5. README 与 YAML 部分注释出现明显乱码，项目名称目录也使用 `Qaunt`（疑似 `Quant` 拼写错误），影响使用和文档可信度。
6. 仓库中曾跟踪大量 `__pycache__/*.pyc` 和运行报告；当前工作区也有大量生成物变化，说明忽略规则和仓库卫生仍需清理。

### P3：测试与交付

1. 在项目 `.venv` 中 60 个测试全部通过；但系统默认 Python 因 pandas/numpy/PyYAML 缺失导致 13 个测试模块导入失败。应提供一条确定的环境自检命令或统一任务入口。
2. 测试以 unittest/mock/合成数据为主；缺少可定期运行的交易所 sandbox 端到端测试、断网/超时/重复响应/部分成功等故障注入测试。
3. 尚未看到 CI 配置、类型检查、lint、安全扫描、覆盖率阈值和依赖漏洞门禁。
4. `requirements.txt` 使用严格版本，但 `requirements.lock.txt` 含大量直接与传递依赖且缺少哈希/平台说明；环境锁定策略不够清晰。

## 建议顺序

先完成实盘安全与对账闭环，再统一领域模型和 Broker/StateStore 接口；随后清理空壳与遗留入口、修正文档编码，最后补齐 CI、故障注入和 sandbox 端到端门禁。在这些工作完成前，项目适合研究、回测和交易所 sandbox，不适合真实资金无人值守运行。
