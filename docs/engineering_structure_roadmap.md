# 工程结构优化路线图

> 核对日期：2026-09-27；依据当前本地工作树和源码。本文是工程实施建议，不是项目阶段验收记录，也不修改任务状态。阶段、依赖和交易准入仍以[统一 Roadmap](unified_roadmap.md)及[开发计划](development_plan.md)为准。工作树中的修改和未跟踪文件尚不能视作 GitHub 已交付内容。

## 目标与现状

结构优化的目标是让一次改动能明确回答四个问题：谁拥有这段行为、数据和配置来自哪里、测试如何证明行为未变、哪个提交包含可复现的结果。优先处理会影响这些答案的边界，再考虑目录外观。

| 现状证据 | 工程含义 |
| --- | --- |
| 当前检出位于 `codex/p2-p3-signal-meta-layer`，HEAD 为 `ab15bc2`；本地存在大量已修改及未跟踪文件，包括代码、文档和工作流。 | 先整理变更身份与范围；不能把本地检查结果直接当成干净检出的 CI 或远端结果。 |
| `core/runtime.py` 提供共享 `EventProcessor`；`backtest/engine.py` 和 `live_trading/engine.py` 仍各自承担运行流程。实时行情、交易所执行与部分运维设施位于 `core/`。 | 已有共享决策逻辑，但“全部模式差异都在外层”尚不是准确的包边界描述。 |
| `core/events/codec.py::_resolve_type()` 延迟导入 `research.audit.ledger` 中的 `CashEvent`、`MarkPriceEvent`；该研究模块声明不接入交易路径。 | `core → research` 形成反向依赖，事件兼容类型与离线账本的归属需要拆开。 |
| `data/binance/1d/` 有 30 个被 Git 跟踪的 CSV；同目录 `_manifest.json` 目前仅记录 BTC、ETH 两个文件。 | 下载缓存清单不足以证明全部入库历史数据的来源、范围与哈希。 |
| `.github/workflows/tests.yml` 安装 `requirements-dev.txt`，并运行锁文件校验；`requirements.lock.txt` 是另一个运行时依赖清单。 | 校验锁文件存在，不等于 CI 的完整依赖安装来自该锁文件。 |
| `live_trading/engine.py` 已抽出 `recovery.py`、`state_export.py`、`tick_orchestrator.py` 等 mixin；`backtest/engine.py` 已抽出 `equity_bookkeeping.py`，但主引擎仍协调较多职责。 | 拆分已有起点，后续应按行为边界和验收证据推进，避免一次性重写交易路径。 |

上述事实只说明本地所见。需区分 **Git 已跟踪版本、当前工作树、干净检出和真实运行证据**；任一层通过，都不能代替下一层的验收。

## 建议顺序

| 顺序 | 工作包 | 主要动作 | 完成条件 |
| --- | --- | --- | --- |
| 阶段 0 · 先行 | 变更集治理 | 保留当前修改，按“文档与仓库卫生、依赖与 CI、数据身份、共享内核、回测、实盘、研究”建立变更清单；对每组记录基线、负责人、受影响文件和验证命令。后续在干净基线的独立分支或工作树做小范围 PR。 | 每个 PR 只承载一个可解释的行为或边界变化；PR 描述能列明输入数据、受影响路径、回归证据与回滚方式；干净检出能复现必要检查。 |
| 阶段 1 · 边界修复 | 消除 `core → research` 导入 | 把事件编码必须识别的 `CashEvent`、`MarkPriceEvent` 契约移到稳定的核心类型模块，或引入仅含类型注册的核心层；研究模块改为依赖该契约。保持历史 `core.ledger:*` 和现有线格式的解码兼容。 | 静态依赖检查拒绝 `core/` 导入 `research/`；旧事件 fixture 能解码，新旧编码的规范化结果一致；回测、回放与沙盒关键测试通过。 |
| 阶段 2 · 数据身份 | 完整数据身份 | 将可变的下载缓存清单与冻结研究输入清单分开；盘点 30 个历史 CSV，逐个记录来源、交易所/账户类型、标的、周期、时间范围、行数、SHA-256 及验证状态。无法证实的文件标记为“未核验”，不补造元数据。 | 冻结清单覆盖被采用的每个输入；哈希与实际文件一致；新增、替换或缺失数据会使验收失败；清单可从干净检出读取。 |
| 阶段 3 · 环境收敛 | CI 安装环境收敛 | 明确 Python 支持版本；为 CI 使用的运行时和开发工具建立可解析的锁定环境，并让 CI 从该环境安装后执行严格校验。保留现有锁校验，但让它验证正在运行的环境。 | 在目标平台的干净检出中安装、锁文件核验、环境严格比对、静态检查和主要测试均通过；锁更新由单独 PR 提交并附差异说明。 |
| 阶段 4 · 逐步实施 | 引擎按职责拆分 | 从纯计算或输出边界开始，分别抽出回测的权益/报告协调、实盘的对账/保护/状态导出等职责；为每次拆分定义输入、输出和状态所有者。保留已有入口兼容，逐次替换。 | 每次 PR 的固定历史回测结果、事件/订单状态、重启恢复和故障注入结果与基线一致；无前视、会计恒等式、UNKNOWN 禁新增风险等不变量仍成立。 |
| 阶段 5 · 稳定后 | 包与文档收敛 | 在上述边界稳定后评估是否将行情、模拟撮合和实盘交易所实现从 `core/` 移至各自适配层；完善可安装包元数据与入口；同步模块文档。 | 导入方向由自动规则约束；旧入口有明确迁移期；安装后的命令、最小使用例和文档路径在干净环境可运行。 |

这里的阶段 0–5 仅表示本文建议的工程处理顺序，不是统一 Roadmap 的 R0–R8。建议将与[开发详情](development_details.md)中 SYS-04 数据身份、SYS-06 模式一致性等契约重叠的改动，挂到相应工作包的证据链；不要用本表自行宣布它们完成。

## 实施约束

1. **先固定观察面。** 对每组改动记录源码提交、工作树差异、配置、数据清单与运行环境。当前工作树有其他进行中的工作；整理时逐文件核对，避免批量清理或覆盖未归属修改。
2. **每次只改变一种边界。** 例如事件类型迁移只处理类型位置与兼容解码；数据清单补齐不顺带更改研究策略或回测参数；CI 锁环境不顺带升级全部依赖。
3. **行为改动与搬迁分开验收。** 机械移动要证明旧入口与事件线格式兼容；真正改变订单、估值或风控语义时，另列设计、迁移和故障回退方案。
4. **以不变量审查交易路径。** 任何跨 `core/`、`backtest/`、`live_trading/` 的调整，都要核对已收盘 bar、Next-Bar 撮合、费用与现金对账、未知订单、新风险门禁、保护单及恢复幂等性。
5. **把结论写到正确位置。** 本文记录工程建议；实际阶段和任务状态写到统一 Roadmap、开发计划及任务登记；历史归档保持历史原貌。代码测试通过不表示策略有效、连续运行达标或真实资金已获批准。

## 首个可交付切片

先完成**变更集清点和 `core → research` 边界修复设计**：列出当前工作树里准备纳入首个 PR 的确切文件，冻结旧事件 fixture，确认类型归属和历史线格式兼容方案。然后做一个只修导入方向的小 PR，并在干净检出里跑事件编解码、回放、回测和实盘订单生命周期相关测试。这个切片完成后，再推进完整数据清单和 CI 锁环境；引擎拆分放到输入、环境、回归基线都可复现之后。
