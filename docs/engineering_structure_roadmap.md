# 工程结构优化路线图

> 核对基线：2026-09-27，公开主分支提交 `ecb94df`。本文列出工程建议与验收条件，不更新项目任务状态。阶段、依赖、策略裁决和真实资金准入仍以[统一 Roadmap](unified_roadmap.md)与[开发计划](development_plan.md)为准。未发布的本地资料和改动不构成公开仓库的完成证据。

## 当前结构与优先问题

仓库已经有清晰的运行主线：`core/runtime.py` 的 `EventProcessor` 共享已收盘 bar 的决策，`backtest/engine.py` 与 `live_trading/engine.py` 分别编排历史运行和实时轮询，`composition/factory.py` 装配策略、路由和风控。结构优化应让这条主线的依赖方向、数据身份和回归证据更容易核查。

| 主分支证据 | 待解决的问题 |
| --- | --- |
| `core/events/codec.py` 解码时延迟导入 `research.audit.ledger` 的事件类型；研究账本声明仅用于离线重放和对账。 | 核心事件编码反向依赖研究实现；迁移要保留历史事件的线格式和旧类名兼容。 |
| `data/binance/1d/_manifest.json` 为已跟踪的 30 个 CSV 各记录了 SHA-256。该目录是可更新的下载缓存。 | 文件覆盖数量完整，但清单本身不是冻结研究输入；还需统一跨平台的原始字节与哈希口径。 |
| 在本次 Windows 检出上，清单哈希与 29 个工作树 CSV 的原始字节一致，`SUI_USDT.csv` 不一致；对 Git 中的文件字节核对，结果相反。将检出文件的 CRLF 统一为 LF 后，30 个文件与 Git 字节一致。 | 换行转换会让同一清单在不同读取口径下给出相反结论。正式复现应明确定义、固定并自动验证哈希所指的字节。 |
| `.github/workflows/tests.yml` 使用 Python 3.11，从 `requirements-dev.txt` 安装并运行锁文件校验；`.python-version` 指向 3.13.2。 | 锁文件通过校验不表示 CI 安装的完整依赖树来自锁文件，也不表示两个 Python 版本的结果相同。 |
| `main.py` 仍内置命令行参数与报告编排，`backtest/engine.py` 仍内置权益与敞口采样；实盘引擎已将 tick、恢复和状态导出拆到独立模块。 | 后续拆分可按变化原因逐步推进，并对订单、估值和恢复行为分别保留回归证据。 |
| 历史/实时行情适配器及模拟/交易所执行的具体实现仍有部分放在 `core/`。 | 共享的是决策流程；包名尚不能代表“所有模式差异都在外层”。 |

上述事实只描述该提交和本次检出。当前工作树、干净检出、远端 CI 与真实运行各有不同的证据边界；不能用一种检查代替另一种。

## 分阶段行动与验收

| 顺序 | 行动 | 验收条件 |
| --- | --- | --- |
| 0 · 变更集治理 | 从最新主分支为每项工作建立小范围变更；为 PR 写明行为归属、受影响路径、数据与配置身份、验证命令、回滚办法。公开文档继续遵守[文档导航](README.md)中的私人资料隔离规则。 | 每个 PR 可独立审查与回退；干净检出能复现所报检查；未发布的历史邮件、审计资料和本地生成物不进入公开提交。 |
| 1 · 修正依赖方向 | 将 `CashEvent`、`MarkPriceEvent` 等事件编码必需的类型契约放到稳定的核心层，再让研究账本依赖该契约；保留历史类名解码映射。一次 PR 只处理类型归属与兼容。 | 自动规则拒绝 `core/` 导入 `research/`；历史事件样本可解码，规范化和重编码结果保持兼容；事件回放、回测和订单生命周期测试通过。 |
| 2 · 固定数据身份 | 明确 CSV 换行与哈希所指字节，制定跨 Windows/Linux 的检出规则；把可更新缓存清单和冻结研究输入清单区分开。冻结清单记录来源、交易所/账户类型、标的、周期、时间范围、行数、SHA-256 与验证状态；无法证实的元数据标记“未核验”。 | 同一提交在目标平台对所采用输入得到一致哈希；文件缺失、替换、范围不符均失败；完整研究包固定实际使用的数据快照及其来源。 |
| 3 · 收敛 CI 环境 | 明确需要验证的 Python 版本，为运行依赖与开发工具定义可安装的锁定集合，并让 CI 从该集合安装后做严格环境比对。依赖升级单独审查。 | 干净检出的目标平台可安装、通过锁文件及环境校验、静态检查和必要测试；锁更新含生成方法、差异说明和复现记录。 |
| 4 · 按职责拆分引擎 | 先从 `main.py` 的参数/报告边界和 `backtest/engine.py` 的纯计算辅助开始；实盘侧在已有 tick、恢复、状态导出边界内继续收紧接口。保持原入口可用，订单和资金路径的语义调整另立变更。 | 每次拆分的固定历史回测、报告、事件、订单状态和故障恢复结果与基线一致；无前视、会计恒等式、`UNKNOWN` 禁新增风险、保护单及恢复幂等性仍成立。 |
| 5 · 稳定包边界 | 在前述回归可复现后，评估是否把模式专属行情、撮合和交易所实现逐步移至对应适配层；补齐安装入口、导入约束和模块文档。 | 导入方向由自动检查约束；旧导入路径有清楚的兼容期；安装后的最小回测与沙盒预检在干净环境可执行。 |

表中的 0–5 只是建议的工程实施顺序，不是统一 Roadmap 的 R0–R8 或任务完成状态。与 [SYS-04 数据身份、SYS-06 模式一致性等任务契约](development_details.md)重叠的工作，应在原任务的证据链中验收。代码测试通过不自动表示策略有效、连续运行达标或真实资金获准。

## 第一个可交付切片

先固定旧事件编码与解码样本，确认 `core/events/codec.py` 对研究类型的现有兼容映射，再提交仅消除 `core → research` 反向导入的变更。在同一 PR 中加入导入方向检查和旧事件回归测试，并在干净检出运行。随后独立处理数据字节口径与 CI 锁环境；引擎拆分安排在输入和回归基线都稳定之后。
