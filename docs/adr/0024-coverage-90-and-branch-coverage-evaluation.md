# 0024 覆盖率门槛提到 90%；分支覆盖暂不设门槛

- 状态：已采纳
- 日期：2026-10-14
- 相关：[质量门槛](../quality.md)，[基础设施路线图](../infrastructure_roadmap.md) C5

## 背景
CI 的覆盖率门槛是 85%（`core ops signal_meta backtest live_trading` 五个包，行覆盖），路线图 C5 要求提到 90% 并评估分支覆盖。2026-10-14 在 Windows 本地（Python 3.13，4025 个测试）带 `--cov-branch` 实测：行覆盖 89.54%、分支覆盖 78.94%、coverage.py 的合并口径 86.64%。缺口集中在：下载与行情的联网路径（`core/market/data_fetcher.py` 约 60%）、`live_trading/tick_orchestrator.py`、`core/trading/position_management.py`、以及一批没有任何直接测试的小型运维工具（例如 `ops/operations/incident_journal.py` 为 0%）。

## 决定
- 门槛提到 **90%**（行覆盖）。为此补了一批有行为含义的测试，而不是只为凑数：事故日志（追加写、拒绝含糊记录）、进程监督（指数退避、稳定运行后重置预算）、Telegram 心跳（无效状态绝不编造财务事实）、R7 与 Phase 6 评估入口（坏证据一律失败并留下记录）、订单状态归一与下单异常分类（决定"不确定结果"要不要先对账）、SQLite 快照与恢复守卫（账户身份、模式版本、损坏目标的取证保留）、补帧与冷却回放（历史帧恢复状态但不产生订单副作用）、入场闸门的各项拒绝原因、公共行情缓冲的数据校验。补测试后行覆盖约 90.5%，其间发现的行为与预期不符之处都是测试的假设错了，没有改动生产代码。
- **分支覆盖暂不设门槛。** `--cov-branch` 把分支并入同一个百分比，`--cov-fail-under` 不能分别对行和分支设限；若直接启用，门槛口径变成合并的 87.4%，要么低于 90% 而失败，要么把门槛降到失去约束力。改为每季度本地跑一次 `--cov-branch` 记录数字（见质量门槛页），分支覆盖低的模块作为补测试的线索。
- 不改 `scripts/main_acceptance.py` 里 55% 的历史验收门槛：它属于另一条历史验收链，与 CI 门槛无关。

## 备选方案
- 保持 85%：不会再有人补上没人测的恢复工具。
- 一步提到 92% 或更高：本地与 CI 之间有零点几个百分点的差异，没有余量就会变成不稳定的失败。
- 启用分支覆盖并用单独脚本分别核对行与分支：可行，但需要在 CI 上先观察分支覆盖的平台差异和运行时开销；等有一个季度的记录再决定。

## 后果
- 本地（Windows）约 90.5%，CI（Linux）预期相近但没有实测；若首次 CI 跑出低于 90%，处理办法是继续补测试，不是降门槛。
- 以后新增的代码如果大量缺测试，会比以前更早被门槛挡住；覆盖率下降时优先看 CI 日志里的缺失行，而不是重跑。
