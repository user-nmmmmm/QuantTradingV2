## 问题

`register_bound_successor` 只在前段查看 `.json.opened`，末段只比较父协议 JSON。样本打开先独占创建回执再重写 JSON，登记可能在两步之间接受旧的 pending 协议。仅在末段再检查一次仍存在检查与发布之间的竞争。

登记又直接写入正式输出目录。复制、生成协议或写回执时失败，会留下不完整目录；按同一路径重试因目录已存在而失败。

## 决定

1. `register_bound_successor` 与 `open_prospective` 使用同一协议路径旁的 `.lock` 文件，持有操作系统的独占、非阻塞锁。锁覆盖协议读取、核验与最终发布／打开；竞争者收到 `BlockingIOError`，稍后重试。Unix 使用 `fcntl.flock`，Windows 使用 `msvcrt.locking` 的一个字节范围；关闭句柄或进程退出释放锁。
2. 锁文件保留，避免删除后另一个进程锁住不同文件。空的 `.lock` 文件只用于协调，不能当成样本已打开；`.opened` 仍是不可撤销的打开凭据，登记不创建、不删除它。
3. 六个登记文件先写到输出父目录下随机命名的 `.名字.registration-*` 暂存目录，包含最后的 `acceptance.json`。核对复制后的实验登记摘要，并在完整构建后复查父协议字节、`.opened` 与父实验登记摘要。
4. 发布时另外锁定目标路径，拒绝任何已有文件或目录，再在同一文件系统内重命名暂存目录。并发登记即使来自不同父协议，也不能覆盖已提交目录。调用者应只把正式目标目录中的完整回执作为登记结果。
5. 普通异常与 `KeyboardInterrupt` 清理暂存目录并释放锁。发布前被强制终止时可能留下隔离的暂存目录，正式目录仍不存在；操作系统释放锁，下一次调用使用新的暂存目录，能够直接重试。遗留暂存目录不作为已登记证据，也不自动据此恢复／重放登记。
6. 发布完成后的同路径重试继续报 `FileExistsError`，保留原有拒绝覆盖的契约。调用者可检查已有完整回执，不能通过重试改写已启动的观察时钟。

协调针对使用本版入口的进程和支持这些锁的本地文件系统；手工改写或旧版工具不参与锁协议。发布前的复查会拒绝检测到的外部变化。原子重命名保证进程中断时的目录可见性，不宣称断电后的持久化恢复能力；未引入网络文件系统的锁保证。

标准库契约：[fcntl 的非阻塞锁](https://docs.python.org/3.11/library/fcntl.html#fcntl.flock)、[Windows 字节范围锁](https://docs.python.org/3.11/library/msvcrt.html#msvcrt.locking)、[同文件系统重命名](https://docs.python.org/3.11/library/os.html#os.rename)。

## 回归验证

`tests/test_bound_successor.py` 使用合成 Git 标签、父协议和配置，不读取真实样本：

- 末段出现打开回执、协议或实验登记改变时，拒绝发布。
- 复制、身份绑定写入、协议生成、验收回执写入和发布前，分别注入 I/O 故障与键盘中断；正式目录不存在，清理后同路径重试成功。
- 用真实子进程暂停在复制后：样本打开和第二个登记均被锁拒绝；完成后六个文件一次性可见，父协议仍可按原有规则打开。
- 样本打开进程已写 `.opened`、尚未重写 JSON 时阻止登记；强制终止后，登记仍因持久打开回执被拒绝。
- 强制终止尚未发布的登记进程后，父协议和打开状态不变，正式目录不存在，重试成功。
- 不同父协议并发向同一目标登记，以及构建过程中出现已有目标，均保留已存在输出。
